    Communication Models:

        Synchronous Request and Response - AKA Blocking
            - wait for the service to do something.
            - latency subject to chaining(when invoking multiple services).
            - is difficult to determine the latency you will be exposed unless you have
            insights into the internals of other services.


        Asynchronous Request and Response - AKA Non-Blocking
            - reduced latency. the client makes a request, and it can do some other processing
              whilst awaits for the response.
            - complexity: match responses to requests and how to handle responses error
              or responses that don't return in a timely manner.


        Event Driven Communication (Async)
            - No response. The service is simply broadcasting events or commands via messages.
            - loosely coupled: we don't need to know about other microservices. Neither if there is
              another service listening to our service.
            - We use Kafka in this approach.

    Kafka & JMS & AMQP
    Alternative Messaging Technologies

            Push vs Pull

        JMS: is an API not a protocol. Is still a viable messaging solution. Uses a push mechanism.

            Two messaging models:

            - Queue (Point to Point)
                - Producer => Queue => Consumer.
                - In a queue each message has only one consumer.
                - If the consumer is not available the queue retains the message. No messages are lost.
                - Once a message is read by a consumer, it is removed from the queue.

            - Topic (Publish/Subscribe)
                - The topic can have multiple consumers for each message.
                - Doesn't retain messages. The message is dropped if there is no active consumer.
                The consumer will never see that message.
                - Messages can easily be lost.

            ActiveMQ
                - uses virtual topics that is a hybrid of queues and topics.
                - backing each topic with a queue, so there is a persistence.


        AMQP: there is no API here because it is a wire level protocol.

            - Producer =>      Broker        => Consumer
                        Exchange -> Queues  
                        [Routing]

                            ---Store----

            - The message is sent from the producer to the broker.
            - An exchange is registered within the broker.
            - The exchange type and binding rules define the routing behavior.
            This combination determine to wich queue or queues the message is then sent.

            - Exchanges types:
                - Direct: The message key within the message is used to direct messages to the consumers.
                - Fanout: Sends a copy of the message to all queues bound to the topic. Routing key is ignored here.

            - AMQP Implementations: RabbitMQ, Apache Cupid
                - AMQP and RabbitMQ has been seen to be more performant than JMS due to feature such as
                batching of messages, binary message format and advanced routing features.
                - RabbitMQ uses a push mechanism.


        Kafka: Uses a pull mechanism.

            - Push mechanism
                - This model is geared towards speed by sending messages to the client.
                - Messages pushed to consumer immediately.
                - Overwhelmed consumers, when the producers send messages faster than the consumers can process them(backpressure).
                - There is some backoff patterns that can help mitigate the consumer being overwhelmed, but these can be quite complicated.
            
            - Pull mechanism
                - Consumer polls for the next message.
                - The performance risk is to have a busy wait loop. This happens when there is no data for the consumer, so it continually pulls.
                - In order to prevent this, Kafka implements a long wait mechanism.
                - Furthermore, to improve efficiency,Kafka implements a batching mechanism, and this results in fewer network calls.
                - So the consumer is also working at a pace that it can handle. 
                - The broker absorbs any backpressure so as not overwhelmed the client.

            - Message Retention
                - In Kafka we use the concept of LOG rather than topic.
                - Kafka uses an append only log for recording messages and maintains a consumer's read position in the log using a pointer kwown as OFFSET.
                - Using a log and a read pointer means that all messages can be retained for as long as configured. This could be for a few days of indefinitely.
                - Retaining the messages opens up the possibilities of message Replay. This means you have the ability to process some or all of the previous messages.
                - This leads to being able to recreate system states based on past events.
                - Scenarios such as creating a new service instance or being able to replay data to help diagnose system issues.
            
            - Ordering
                - Sometimes it is important to process messages in the order in which they were produced.
                - Ordering is possible with each of the implementations: JMS, Rabbit, Kafka.
                - But Kafka is the only one that can combine ordering with scaling.
                - In Rabbit ordering is guaranteed only when the message published in one channel.
                - In JMS we've dedicated consumers. This is possible, but not when involving multiple consumers.
                - Kafka supports ordering via the message key and its use of partitions(form part of the log).
                - The message is on a single partition and it will be processed by the same consumer.
                - We are not using a dedicated topic, it means that the topic can still have multiple consumers and so scaling.
                - But those other consumers will be reading from different partitions, thereby maintaining order on the partitions and still allowing scaling through multiple
                consumers on that very same topic.
                - Message ordering is guaranteed with Kafka in which scenario?
                    Messages are writeen with keys ensuring related messages are sent to the same partition.
                    By writing related messages to the same topic partition, Kafka is able to guarantee ordering.

    What is Kafka?

        An introduction to the key concepts and architecture

        Index:

            - Consumer Groups
            - CLusters

        Why you are using Kafka?
            - Publish Subscribe Messaging
            - Realtime Stream Processing
            - Fault Tolerant
            - Highly Available
            - Highly Scalable
            - High Throughput


        Producer to Consumer

            - Producer (Sends to Broker) => Broker (Message store) => Consmer (pulls from Broker)

        Topics
            
            - Ordered sequence of events, it is a persistence record of events. AKA log.

            - Producer  =>    Broker    => Consumer
                            - Topic A
                            - Topic B

        Log
            - All events are recorded in the log. An event helds its position subject to the retention period.
            - The log is inmutable, wich means the content will not cannot be changed.
            - Events remain in the topic, so we have the OFFSET, it is a reference to our read position.
            - The broker maintains the next read position via the OFFSET.


        Partitions
            - The topic it's actually split into a number of logs. These logs are referred to as partitions.
            - Partitions allow parallelism for producers and brokers. And this parallelism enables the high throughput.
            - The same key on multiple messages will mean that same messages are placed on the same partition.

        
        Consumer groups
            - Allow multiple consumers to collaboratively process messages from topics by dividing topic partitions among themselves.
            - Only one consumer in the group consumer will consume a message.
            - Each partition will be assigned to only one consumer in any one consumer group so messages are not shared.
    

        Cluster
            - A cluster contains multiple Brokers
            - It guarantees Kafka's resilience.
        

        Replication
            - Partition level replication
            - load distribution.
            - if a broker node fails, then we've not lost any of the data.
            - It is still available in another node.
            - Replication is achieved when events from the leader partition are replicated to the follower partitions.
            - Messages are replicated across broker nodes to ensure Resiliency.

    Messages & Events

        - What is a Message? What is an Event?
            - The message is the envelope that carries the payload.
            - The Message(or Record) is the envelope and the Event is the letter withint the envelope.
            - The payload can be an event or a request.
            - An event represents something that has happened

        - Requests or Commands?
            - A request/command indicates that a consuming service should do something
            - Both are asking for an action to occur. E.g instruct the consuming service to dispatch payment.
            - An 'ask' does not guarantee an action will occur.
            - There is no guarantee a request will be actioned.

    What is a Kafka message?

        - Key
            - Providing a Key is optional.
            - Default key is null.
            - If there is a null message key there is no guarantee in which partition the message will be written to.
            - Key facilitates guaranteed ordering.
            - If a message is written to a topic with a key, then it will be written to the same topic partition as other messages with
              the same key.

        - Headers
            - Key value pair, event metadata.

        - Payload (Value)
            - String, Json or Avro. Anything that can be represented as an array of bytes.
            - Max default size: 1mb

        - Payloads - what should be in there?
            - Protecting data not oversharing.
            - Sufficient data for Consumers.

    ZooKeeper & Kraft (Cluster metadata management)

        - ZooKeeper (now deprecated)

            - Is an open source tool for maintaining synchronization of configuration in distributed systems.
            - ZooKeeper manage the metadata required to run a Kafka cluster that included tasks such as:
                - Identifying the brokers within the cluster.
                - Monitoring the brokers status and health. Which brokers are recently started? Are the brokers in the cluster sill available?
                - Topic management such as:
                    - Creation and deletion of topics.
                    - Leadership election topics.
            - Why leave ZooKeeper?
                - Running ZooKeeper to manage the metadata requires a cluster of at least three ZooKeeper nodes.
                - Large deployments would have many more ZooKeeper instances, and that's a lot of java processes to manage, creating a huge administration cost.
                - These processes are storing metadata about the Kafka cluster outside the Kafka cluster, does not make sense. It represents a duplication.
                - The transfer of this metadata state between ZooKeeper and Kafka take can considerable time.
                - These reasons and the impact on scalability meant that a new solution was required.


        - Kraft (Apache Kafka Raft)
            - Manages clustering data.
            - Internalisation of Metadata which means cluster management without external assistance.
            - Simplified Admin: This is a much simpler model to administer because Kraft removes the need for an external application.
            - Event Based Management: Kraft uses an event based consensus protocol using logs like Kafka uses logs.
            - Improves the cluster management by reducing metadata duplication, communication overheads and removing the scalability limitations.

    * Running Kafka

            - KAFKA_CLUSTER_ID="$(bin/kafka-storage.sh random-uuid)"
            - echo $KAFKA_CLUSTER_ID   ---->  some random alphanumeric value

        - We need to format the log directory location. This is a directory that will be used for the persistent store of the message topics and all the metadata for Kafka.
            - bin/kafka-storage.sh format -t $KAFKA_CLUSTER_ID -c config/kraft/server.properties  ----> this will now set up the log directory in the default location of /tmp/kraft-combined-logs
            - /tmp is not the best location as this folder often gets cleaned up when the machine is rebooted. Change the location to a folder that is longer lasting. If you want to do that change
              of directory, you need to edit the server.properties file and modify the log.dirs setting.  

        - OPTIONAL at the beginning, define message topics metadata location with default config:
            - rm -rf /tmp/kraft-combined-logs   ----> in case the existence id is different and represents conflicts (sometimes it throws an Exception)

        - Start the server
            - bin/kafka-server-start.sh config/kraft/server.properties

        - Sending and Receiving
            - note: "." and "_" is equal in Kafka
            - Open 2 terminals, each one for consumer and producer

            - In consumer console:
                - bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic my.first.topic
                    -> a warn terminal message appears and indicates that our topic is not created and Kafka creates for us.

            - In producer console:
                - bin/kafka-console-producer.sh --bootstrap-server localhost:9092 --topic my.first.topic
                    > my first message    ---->  enter and the message appears in consumer console. I noticed that the topic is created when the message is sent, not before.
            - Ctrl + c in both consoles to finish

            - In other window: bin/kafka-server-stop.sh   ---> the server is stopped


--------------------


    * CLI Tools - Topic Tools

        
        Topic CLI Tool can be used for list, create, modify, delete and view details of a topic.

        bin/kafka-topics.sh --bootstrap-server localhost:9092 --list                                           ---> list the topics. __consumer_offsets is used to store info about committed offsets for each topic and partition. 

        bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --topic my.second.topic                 ---> create a new topic

        bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic my.second.topic               ---> shows information of the topic

        bin/kafka-topics.sh --bootstrap-server localhost:9092 --alter --topic my.second.topic --partitions 3   ---> modify the number of partitions within the topic. The topic name cannot be changed.

        bin/kafka-topics.sh --bootstrap-server localhost:9092 --delete --topic my.second.topic                 ---> to delete a topic 


--------------------


    * Consumer Group CLI Tool

        - A consumer group is a collection of consumers working together to consume messages of the partitions of the topic.


        bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --topic cg.demo.topic --partitions 5     ---> create a new topic with five partitions

        bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic cg.demo.topic

        bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --list                                    ----> shows the consumer groups(until here is empty)

        (In a new console)
        bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic cg.demo.topic --group my.first.consumer.group
        
            - To setup a new consumer associated with the specified consumer group


        bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group my.first.consumer.group

            - shows the details of the consumer group
            - CURRENT-OFFSET: Is the last committed offset of the partition
            - LOG-END-OFFSET: Is the highest offset of the partition
            - LAG: Is the number of not consumed messages on the partition

        Execute this again in another console to have two consumers listening to the specified topic:

            - bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic cg.demo.topic --group my.first.consumer.group


        bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group my.first.consumer.group

            - shows that one of the consumers is listening to messages on partitions 0,1 and 2. Additionally, the other consumer is listening
              on partitions 3 and 4. This is called re-balancing(a process that is executed when a consumer is join or leave a CG
              or when number of partitions is changed).

        
        bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group my.first.consumer.group --state

            - shows the state and health of the Consumer group. Until this point the CG has 2 members.

        
        bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group my.first.consumer.group --members
        
            - shows details of the consumers within a consumer group
